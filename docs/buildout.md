# Buildout — delivering the framework

    Status: ACTIVE
    Authority: docs/concept.md. Where this document disagrees with the concept, the concept wins.

The sequence that takes this repository from four markdown files to a plugin other solutions
can install and use. It is finite: when phase 9 lands, this document is archived rather than
maintained.

## How this is built

**As an ordinary product.** Branch, review, merge. This repository runs no cycles on itself and
has no `.sdlc/` directory. Skills are written as deliverables and validated against fixtures,
the same way any library is written and validated against tests.

**Fixtures are the substrate.** Every skill needs an input to run against and an expected
result to be graded on. Those are checked-in, hand-written, and disposable — never generated by
the framework, because test data produced by the thing under test proves nothing. Fixtures come
before the first skill for that reason.

**Verification is integration-first.** All twelve skills are written, then the cycle is walked from
intent to landing against a fixture and fixed where it breaks. Polishing each skill alone would find
the wrong class of defect: the risk is in the handoffs — what one phase writes and the next cannot
read — not in any single skill's prose.

**Skill tests are not a phase.** Every skill ships with its cases in the same pull request. A
skill without cases is not done.

A case runs Claude headlessly against a materialized fixture and asserts on the artifacts it
produced — `claude -p "/sdlc:<skill> …"`, then check the files. Not `claude plugin eval`: it is
early access and unavailable on this account, so building on it would block the whole plan on
something outside our control. Reconsider when it reaches general availability; the fixtures and
expected results transfer either way.

**Nothing operating across many cycles is built until one cycle works.** Batch mode, the
suggestions view and adoption all wait for phase 6. One working chain teaches more than eleven
half-built skills.

## Phase 0 — an installable, checkable shell

**Status: done** — `f1ab05d`. The GitHub path is verified: `claude plugin marketplace add
MofonCode/ai-sdlc` clones and installs with 12 skills and the hook loaded. Still unverified on a second
machine, which needs a second machine — what that would add is whether anything here depends on this
one's state.

Nothing can be validated until the plugin loads, and nobody else can install it until the
GitHub path works.

- `.claude-plugin/plugin.json` — name `sdlc`, displayName `ai-sdlc`, author, keywords
- `.claude-plugin/marketplace.json` — so both a directory source and the GitHub source resolve
- `.gitignore` — build output must not reach a directory-marketplace install, which copies the
  working tree rather than the committed one
- `.gitattributes` — normalize line endings in the repository, so contributors on different
  machines do not see whole-file diffs
- `.github/workflows/ci.yml` — `windows-latest`, installs the CLI, and validates both manifests
  as **hard gates**. v02 ran these advisory because the CLI was not guaranteed on a runner, and
  two manifest defects shipped green through exactly that gap
- Tooling lives in `tools/`. Never a top-level `bin/`: files there join the Bash `PATH`, and
  claude.ai and Cowork refuse to install a plugin that has one

**Done when** both manifests validate, the plugin installs from the GitHub marketplace on a
machine that is not this one, and CI is green.

**Known warning:** a `CLAUDE.md` at the plugin root is not loaded as plugin context, and the
validator reports it. It exists for people working in this repository, because Claude Code reads
`AGENTS.md` directly only from v2.1.277. The plugin manifest is therefore validated without
`--strict` until that version floor is acceptable for every contributor, at which point
`CLAUDE.md` is deleted, its content folds into `AGENTS.md`, and `--strict` returns.

## Phase 1 — the rules and the vocabularies

**Status: done** — `7dd8b19`. Eleven constraints, two schemas, nine fixtures.

Skills enforce constraints and branch on schema enums, so both precede the first skill.

- `constraints.md` at the plugin root — the global constraints, `CON_nn`, each with a non-empty
  `Forbids:`. Target eight to ten; every candidate passes the three tests in concept §4.2 or is
  moved to a hook, a schema, or an analyzer
- `schemas/findings.schema.json` — the `severity` enum is the single definition of the taxonomy
- `schemas/verify.schema.json` — the `outcome` enum: `pass`, `blocked`, `escalated`

**Done when** a hand-written findings document and verify document both validate against their
schemas, and no constraint in the file would be satisfied by every possible implementation.

**Open: where schema validation permanently lives.** Phase 1 validated with `ajv` installed in a
scratch directory, which proves the schemas and nothing else. The durable validator belongs in
the repository and in CI — `JsonSchema.Net` from a .NET test project is the Microsoft-first
answer and supports draft 2020-12. Decide it with the phase 2 harness, not before.

## Phase 2 — fixtures and the harness

**Status: done** — two fixture solutions, nine golden artifacts with expectations, the
`FixtureWorkspace` harness, and 27 tests. Both deferred decisions are settled: the harness is a
.NET MSTest project, schema validation uses `JsonSchema.Net`, and frontmatter is read with
`YamlDotNet` rather than a regex. Which PowerShell edition hooks target is still open and now
binds at phase 5.

The test substrate. Without it every later phase is validated by eye.

- `tests/fixtures/solutions/greenfield/` — a minimal .NET solution with a `.sdlc/solution.md`
  and no history
- `tests/fixtures/solutions/brownfield/` — a solution with existing code and history, to prove
  that adoption is free and that pre-existing code does not block a first cycle
- `tests/fixtures/artifacts/` — golden artifacts, good and bad, each paired with the findings it
  must produce: a solution-shaped intent, a spec with an untestable criterion, a spec that
  introduces scope the intent never asked for, a plan that names no proof for a criterion
- `tests/Sdlc.Tests/FixtureWorkspace.cs` — materialize a fixture into a scratch directory as a
  git repository, so a skill runs against a disposable copy and never mutates the checked-in one.
  C# rather than PowerShell: the harness is test code, and the test project already exists for
  schema validation

- `schemas/expectation.schema.json` — what an interrogation of a golden artifact must conclude.
  Assertions are on which constraints are cited at which severity, never on wording: wording is
  model output, and asserting on it would make every case brittle

**Done when** a fixture can be materialized, mutated, and discarded in one command, and every bad
artifact has its expected findings recorded beside it.

## Phase 3 — interrogation and intent

**Status: done.** interrogate verified 9/9 against the golden artifacts; intent verified end to end.
Walking the flow found eleven defects that reading it never would, all now fixed:

1. **A solution session cannot read the plugin root.** Every skill that needed the global constraints
   failed outright — and would fail hardest unattended, where nobody can approve a directory. The fix
   is a load-time shell injection: `tools/Get-Constraints.ps1` runs with the harness's privileges and
   the rules are in the skill body before the model is asked anything. Asking one skill to invoke
   another was tried first and does not work.
2. **Reference data last buries the instruction.** With the constraints injected at the end,
   interrogate reached the right verdict and printed it instead of writing the file. Reference data
   first, procedure last.
3. **The integrity hook blocked the artifact's own producer.** Denying every write under `findings/`
   stopped interrogate writing its findings. A hook cannot tell a producer from a person by the call,
   so it now keys on what does distinguish them: Edit versus Write for a verify document, creation
   versus overwrite for findings and evidence.
4. **A model cannot read a clock** and writes a plausible midnight. The injector states the time.
5. **Judging on a constraint's heading rather than its `Forbids:` clause.** CON_04 fired on a spec
   that had a criterion for every outcome, because one was vague — which is CON_03's breach. The
   clause is the operative text and is deliberately narrower than the heading.
6. **An unresolvable cross-reference degrades silently.** A spec naming `intent: intent.good.md`
   instead of a repository-relative path could not be bound to its intent, so the relational
   constraints were skipped and the verdict came back *sound*. Interrogation now refuses rather than
   judging what it can reach, and the spec and plan skills state that the reference is a path.
7. **CON_04 did not say that must-not-change items are outcomes**, so a spec dropping a
   compatibility requirement passed. Clarified in the clause.
8. **A skill cannot invoke another skill.** Every skill ended with "then run `/sdlc:X`" and every one
   of those calls errored. A chain that only sometimes fires is worse than none: it produces artifacts
   nobody challenged while appearing to have challenged them. Skills are now single-purpose and name
   the next command; chaining belongs to whoever is driving, and `run` drives it as one headless
   session per step.
9. **Nothing recorded acceptance.** The spec skill refused unless a person had accepted the intent,
   and no field existed to say so — only the plan had `approved_by`. `accepted_by` and `accepted_at`
   now mirror it on intents and specs, both fields or neither.
10. **The intent skill stopped stating its own frontmatter**, lost while stripping unreachable paths,
    and produced intents with none at all. A test now asserts that each skill mentions every field its
    artifact's schema requires.
11. **The generative skills could not see the constraints** and were visibly trying and failing to read
    them. spec, plan, build and verify now receive the same injection interrogate does, so what they
    write is written to the rules — interrogation is still the gate.

The golden artifacts were also rewritten twice, for the same reason both times. **An interrogation
reads the code, so a golden artifact must be true of the fixture solution it is placed in.** The first
set described a dashboard the fixture does not have; the replacement claimed two guarded call sites
that did not exist, and CON_02 correctly fired on the artifact meant to be sound. Each artifact now
isolates one constraint — a fixture tripping two makes a failure ambiguous — and the fixture carries
the callers its artifacts refer to.

No test can check that coherence: it is semantic, and the only thing that catches it is running the
flow. So a new fixture is not finished until it has been interrogated once and the result read.

- `skills/interrogate/SKILL.md` — challenge an artifact against the effective constraint set and
  emit findings that validate against the schema
- `skills/intent/SKILL.md` — the interview. Elicit rather than draft; convert a solution-shaped
  request into a problem, and demote any decision already made to a recorded constraint with
  attribution rather than letting it become the intent's content
- Eval cases for both, run against the phase 2 artifacts

**Done when** interrogating each bad fixture artifact produces the findings recorded beside it,
and no findings on the good ones.

## What the first trial run found

A greenfield cycle was run end to end on a real repository at `0.1.0`. The core held: all eight findings
documents were schema-valid, the file set matched the plan exactly, the evidence was genuine, and CON_07
fired for precisely the right reason — content inside a declared file, the one thing a hook cannot see.
Eighteen defects came out of the edges, and `0.2.0` is the result.

**The meta-defect, fixed first.** Nothing validated a live artifact: schema checking existed only in the
test project, against fixtures. That is how a verify document with twelve schema errors shipped looking
authoritative, and it meant the state machine the schemas encode had never once guarded anything real.
`tools/Assert-ArtifactShape.ps1` now refuses a write whose top-level keys contradict the schema, reading
the schema at run time so there is no second definition to drift. It checks names, not values — the
conditional rules still need a real evaluator, which Windows PowerShell 5.1 cannot be — so the deep
check stays in the test project. Shallow and immediate, plus complete and slower.

**The diagnosis that explains most of the rest.** `interrogate` carries a worked example of its output
and produced eight valid documents out of eight. `verify` and `init` carried none and both produced
invalid ones. Every skill that writes a schema-governed artifact now shows the shape it must write.

**`init` was the worst offender**, with six. It never committed its own output, so `AGENTS.md` was
untracked when the cycle took its diff, the diff recorded all 52 lines as new, and a plan saying it
*changes* that file could not match — the first cycle failed CON_07 for something adoption did. It wrote
an `AGENTS.md` asserting the repository was empty *and* a note telling a reader to delete that paragraph
later, which is an instruction that outlives the truth it described. It wrote `adopted_on`, which the
schema forbids. It chose `origin: adopted` for a repository holding one empty commit, because it read
"has history" as "has commits" rather than "has code". It created `.gitkeep` files nothing removes. And
it wrote no guide for whoever has to work in the adopted solution.

**A fixture asserting a judgement will flake.** After the refactor `plan.good.md` drew a CON_06 finding
on one run and none on the next, with nothing in between. CON_06 asks whether a proof is *adequate* to
its criterion, which is the constraint that most needs reading comprehension and therefore the one with
real variance. The expectation framework treats any unexpected blocking finding as a failure, which is
right for CON_01 through CON_05 and too strict here. A disagreeing case should be re-run and reported as
flaky rather than either retried silently or recorded as a defect — hiding the variance is the same
mistake as an advisory gate.

**Identifiers and layout changed on usability grounds.** Ids are underscore-separated so a double-click
selects the whole of one, and everything about a cycle now lives in one directory with a single
`findings/` folder beside the artifacts. The old split put an intent somewhere else with findings of its
own, for a reason — an intent can be rejected before a cycle exists — that turned out not to be worth
two places to look.

## Phase 4 — the artifact chain

**Status: verified on the happy path.** A one-line problem description became a sound intent, a sound
six-criterion spec, and a sound plan that chose `tier: contract` on its own because the change moves a
public signature — each surviving interrogation with no findings, and each refusing to accept or
approve its own output. Not yet tested: a deliberately vague intent, where the spec must block on an
open question rather than invent a criterion.

- `skills/spec/SKILL.md` — accepted intent to testable acceptance criteria, answerable to the
  intent in both directions: covering every outcome it asks for and introducing none it does not
- `skills/plan/SKILL.md` — spec to a plan that declares every file it will touch, a
  blast-radius tier, and how each criterion will be proven

**Done when** a spec and plan generated against the greenfield fixture survive interrogation,
and a spec written against a deliberately vague intent produces blocking findings rather than
inventing criteria.

## Phase 5 — execution and audit

**Status: written, unverified.** Hooks target Windows PowerShell 5.1: a hook that cannot start because an edition is missing protects nothing while appearing to.

- `skills/build/SKILL.md` — implement an approved plan and self-heal build and test failures.
  Nothing leaves build that does not compile and pass
- `skills/verify/SKILL.md` — adjudicate the diff against the spec, report every unmet criterion
  as `blocking` or `suggestion`, derive every claim from evidence that already exists
- `hooks/hooks.json` with the integrity hook: **a verify document is never hand-edited.** This
  is the most load-bearing hook in the design — the whole audit story rests on verify being
  derived
- The PowerShell the hooks call, in `tools/`

**Done when** a plan is implemented against the greenfield fixture, `verify` writes an outcome
derived from real build and test output, and an attempt to edit `verify.md` by hand is refused.

## Phase 6 — the first complete cycle

**Status: written, unverified.** This is the milestone — the flow walked end to end, and a deliberately unfixable fixture escalating.

- `skills/remediate/SKILL.md` — work the blocking findings, bounded at three passes, each
  followed by a full verify. The counter resets only when a human changes an input
- `skills/land/SKILL.md` — open the pull request; refuse an `escalated` cycle and report how
  many remediation passes were spent
- The gates: no landing while escalated, and the diff touching only files the plan declared

**Done when** a cycle runs intent to pull request on the greenfield fixture with no manual step
between phases, *and* a fixture designed to be unfixable escalates after three passes with
landing refusing it. Both halves are required — a framework that only demonstrates the happy
path has not been tested.

## Phase 7 — adoption

**Status: written, unverified.**

Deliberately after phase 6: `init` scaffolds a shape, and the shape is only proven once a cycle
has run end to end on it. Building it earlier means scaffolding a guess.

- `skills/init/SKILL.md` — scaffold `.sdlc/`, `solution.md` and a lean `AGENTS.md` into a
  repository
- `docs/techstack.md` — the default stack as reference: project shapes, pins, layout

**Done when** `init` run against an empty repository produces the greenfield fixture's shape, and
run against the brownfield fixture leaves its existing code untouched and its first cycle
unblocked by anything that predates adoption.

## Phase 8 — scale

**Status: written, unverified.**

- `skills/run/SKILL.md` — batch approved plans, one worktree per cycle
- `skills/constraints/SKILL.md` — render the effective set, library globals merged with solution

## Phase 9 — the checks that keep it honest

**Status: partly done.** 41 tests cover the docs index and freshness, constraint integrity and stack neutrality, manifest shape, hook-script existence, and skill frontmatter read by a real YAML parser. Outstanding: validating the verify documents a real cycle produces.

- The docs freshness check: `covers:` globs compared against source commit dates, with
  `freshness: exempt` honoured
- The index parity check: every file under `docs/` appears in the `AGENTS.md` index exactly
  once, and every row points at a file that exists
- Constraint referential integrity: every `Superseded-by` names an ID that exists, and no ID is
  reused
- Tests for the PowerShell in `tools/`

**Done when** a stale doc, an orphaned doc, a dangling supersession, and a reused constraint ID
each fail CI.

## Sequencing risks

**Phase 1 is the one that can fail outright.** If fewer than about six constraints survive the
three tests, the adversarial enforcement mode is not carrying its weight, and the honest
response is to narrow it to a single interrogation of specs rather than keep machinery that is
not justified.

**Phase 2 is the phase most likely to be skipped under time pressure**, and skipping it makes
every later phase unverifiable. A skill validated by reading its output is not validated.

**Phase 6's unhappy path must not be skipped.** Escalation is the behaviour that makes
unattended mode safe to trust, and it is the one nobody demonstrates.

**A second contributor can start at phase 0.** Because the framework is built as an ordinary
product, contributing means writing markdown, PowerShell and eval cases behind a normal pull
request — there is no process to learn first, and no dependency on any phase being finished.

## Constraints cited here

Short descriptions, so nothing here sends you to look one up. `constraints.md` carries the full
statement, its `Forbids:` clause and the reasoning; `/sdlc:constraints` renders the effective set for
a solution, this list plus any `LOC_` of its own.

| | |
|---|---|
| `CON_01` | an intent states the problem, not the solution |
| `CON_02` | an intent's unknowns stay open questions |
| `CON_03` | a criterion can fail |
| `CON_04` | a spec covers every outcome its intent asks for |
| `CON_05` | a spec adds no scope the intent did not ask for |
| `CON_06` | a plan's proof is adequate to its criterion |
| `CON_07` | a change does only what its plan declared |
