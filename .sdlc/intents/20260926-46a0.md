# The charter gate can be walked around with sed

The rule that this document changes only by approved intent is enforced by a `PreToolUse` gate.
**Two layers keep a shell command away from it, and both have to change.**

First, `hooks/hooks.json` registers the gate for `Edit|Write|MultiEdit|NotebookEdit` only, so a
`Bash` call is never routed to it at all. Second, the gate script re-checks the same four tool names
itself and returns no opinion on anything else — deliberately, so that it does not depend on its own
configuration being right. So widening the matcher alone changes nothing.

And there is a trap in the order of the fix. When the gate *does* run, a payload yielding no path it
recognises is **denied**, not passed: it extracts paths from `file_path` and `notebook_path`, and a
shell payload carries a `command` string instead. So widening both layers without teaching the gate
to read a command would deny **every shell command in the repository**. The three changes are one
change.

All four protected paths are exposed, not just the charter: a pack's `pack.yaml`, its
`pack.rules.yaml` and its charter template are protected by the same patterns and bypassed the same
way. The pack template is the worst of the four, because every solution scaffolded from that pack
inherits whatever it says.

**This was found by the charter's own interrogation** — the second round of cycle `20260926-bc24`,
finding `charter-r2-reason15` — while checking a sentence that claimed the gate refuses *any* edit
to a protected path. The claim was false, and the reason it was false is this hole. The sentence has
since been removed; the hole has not.

`caused-by: unknown`, deliberately. The gate was built as bootstrap work outside any cycle, so
there is no cycle to attribute it to, and a guessed attribution pollutes the only unbiased signal
the retro loop has. Worth recording in prose, though: **the defect is in code that never went
through the process**, which is the most interesting attribution available and the one the schema
cannot express.

## What is wanted

Two mechanisms, because neither alone is sufficient.

**Prevention, where a tool can be inspected.** The gate should also be routed shell commands, should
accept them as in scope, and should refuse one that writes a protected path from a branch not
licensed to write *that* path.

**Detection by construction, which no choice of tool can route around.** A mechanical check that
compares the protected paths against a baseline and fails when one differs without a licence. It
examines the *result* rather than intercepting the *action*, so it does not care which tool made the
change, and it cannot be defeated by a spelling the prevention half did not anticipate.

The second is the load-bearing half, and the reason to build it is the same reason the pack is
protected alongside the charter: close the hole *by construction* rather than by enumerating the ways
through it. Prevention is a blocklist and blocklists leak.

### The licence is path-bound, and it is answered in one place

The question is not *does this branch carry a charter intent* but **does this branch carry an intent
licensing a write to this path**. The charter splits the two sources by path, and a licence bound to
the source alone would let a `pack-review` branch rewrite the charter.

One implementation answers it, because two copies of that rule is how a rule starts drifting — the
prevention half and the detection half both ask it.

**It fails closed.** A licence is granted only on positive evidence: anything that cannot be
positively established as a licence is no licence. No intent file, unreadable or invalid
frontmatter, a `source:` that is neither `charter-review` nor `pack-review`, a source that does not
match the path being written — each is a refusal, never a default.

### What the licence proves, and what it deliberately does not

On the shipped gate, a licence proves that a file at `.sdlc/intents/<id>.md` exists on a branch named
for it and declares one of the two permitted sources — **either one, for any protected path**, which
is the cross-licensing hole named above. It does **not** prove a person approved anything, and
`.sdlc/intents/` is not itself a protected path, so a process can write its own intent and satisfy
the test.

**Accepted, with the reasoning, rather than left silent.** An edit on an unmerged branch is a
*proposal*, not an amendment: the charter on master is unchanged until the pull request merges, and
that merge is the human grant. The gate's job is to ensure a protected edit arrives as a proposal
rather than as a fait accompli. A cycle can request; only a person can grant, and the grant is the
merge.

This is why no new protected path is needed, which is what makes the out-of-scope line below hold
rather than rule out its own remedy.

**The wording mismatch is real and is not settled here.** INV-08 forbids amending the charter
"outside an approved charter or pack intent", while the gate enforces *declared*, not *approved*. If
the reading above is right, the invariant's wording is what is loose. Reconciling it is a charter
amendment and belongs to its own intent — this one changes no invariant.

## How we will know it worked

- A shell command that writes `.sdlc/CHARTER.md` is **refused** on `master`, and the refusal names
  the path and says what would permit it.
- The same command is **permitted** on the branch of an intent whose source is `charter-review`.
- A shell command that writes a pack's `pack.yaml`, `pack.rules.yaml` or charter template is
  permitted only on the branch of an intent whose source is `pack-review`.
- **The cross cases are refused**: a `pack-review` branch writing the charter, and a
  `charter-review` branch writing pack files, are refused exactly as an unlicensed branch is.
- A branch whose named intent is **missing, unreadable, or declares another source** is refused.
- **An ordinary shell command is unaffected.** This is the criterion most likely to be broken by the
  fix, and the one that would break everything, because the gate denies a recognised tool yielding no
  recognised path. A command that touches nothing protected must pass, and **a command that merely
  reads a protected path must pass** — naming a protected path on a command line is a normal, healthy
  occurrence, so the heuristic has to distinguish a read from a write rather than matching the path.
- A protected path that differs from its baseline, on a branch with no licence for it, produces a
  **blocking finding** citing the amend-only-by-approved-intent invariant — blocking rather than
  advisory, through that invariant's `charter-violation` route.
- **One licence answer, provably.** A test asserts both mechanisms resolve the licence through the
  same shared function, and a construct check fails a second implementation of it. Without an
  observable criterion, "answered in one place" is indistinguishable from two copies that have begun
  to disagree.

## What should happen when it fails

- **A write the heuristic does not recognise gets through.** Accepted, by decision: the gate allows a
  command it cannot classify as a write, because a check that refuses healthy commands is switched
  off and an ignored check is worse than no check. The result-comparing check is the backstop.
- **The heuristic refuses something harmless.** More serious than the above, because it erodes trust
  in the gate. A false refusal is a defect to be reported and narrowed, not worked around by
  disabling the matcher.
- **An unlicensed branch is read as licensed.** The silent direction and the worse one: because one
  implementation answers the licence question, a wrong *yes* opens the gate and disables the
  result-comparing backstop in the same stroke, leaving the hole exactly as it was. Hence fail
  closed, above.
- **A licensed branch is read as unlicensed.** Then a legitimate amendment cannot be made, which is
  loud and immediate rather than silent — the failure direction to prefer.
- **No baseline exists to compare against** — no local `master`, a shallow clone, a detached HEAD, a
  fresh worktree. The check reports **skipped, with the reason**, the way the schema validator
  reports a kind no schema governs. It must never read as approval, and it must not fire on a healthy
  repository that simply has no local baseline.
- **The check itself faults** — git unavailable, a ref that will not resolve, an unreadable path.
  Distinct from having no baseline: this **fails**, because a check that cannot run has approved
  nothing. The two outcomes are separate so that a broken check cannot hide inside a normal one.
- **On `master`, there is no merge target distinct from HEAD.** So the baseline there is HEAD itself:
  a protected path differing from HEAD on master is an uncommitted unlicensed edit and fails, while a
  committed difference arrived through a merge, which is the grant. Without this the check either
  never fires on master or fires forever after every amendment.
- **The gate itself throws.** It already denies in that case and must continue to: a protection that
  opens when confused is worse than none, because the charter still claims to be protected.

## What is out of scope

- **`PostToolUse` detection.** It cannot undo a write, and the result-comparing check already covers
  detection at the point where a finding can block.
- **Changing which paths are protected.** The four patterns stay as they are. This holds because the
  licence reading above needs no new protected path; were the licence to require approval rather than
  a proposal, `.sdlc/intents/` would have to be protected too and this exclusion would have to go.
- **Amending the charter.** No invariant changes. INV-08's "approved" wording, and the same loose
  disjunction in its `Forbids:` clause, are raised above and belong to their own charter intent.
- **Whether the harness routes `PreToolUse` for the PowerShell tool.** An official plugin matches
  `Bash`, so that name is real; nothing anywhere matches `PowerShell`, so its behaviour is unverified.
  The gate's *decision* is testable by feeding it a payload directly, which is what will be tested;
  whether the harness delivers such a payload is a separate question to answer from the debug log.
- **The twelve blocking findings still outstanding on the charter** from cycle `20260926-bc24`'s
  second round. They are real, and resolving them is not this intent's business — it changes no
  invariant. They are **owned by nothing**: that cycle reads `done`, because the charter records its
  amendment, so twelve blocking findings are outstanding against no open cycle and need an intent of
  their own. That it landed with them undispositioned is a defect against its landing and deserves
  its own finding rather than a sentence here.
