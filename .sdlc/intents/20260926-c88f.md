# The suggestion half of interrogation is built end to end and reports nothing usable

Eighty-five suggestions exist across two cycles. The signal that is supposed to read them
**fires on seven of eight categories on day one**, the spec that drew thirty-two of them says so
nowhere, and the one category value that means *the taxonomy failed here* is filed as a suggestion
about the artifact.

Three changes, one subject: **what a suggestion is reported as, and to whom.** None of them
reduces the pile, and none of them promotes anything — a suggestion still generates no work until a
person decides it should.

## What is wrong

**1 · The cluster threshold counts findings where it means cycles.**
`tools/Get-SdlcSignals.ps1:293-314` increments once per finding and fires at three. Its own comment
says what it is for — *"a recurring cluster on one theme is the signal that an invariant is
MISSING"* — and recurrence across cycles is the only reading of that sentence which is evidence of
anything. Three suggestions raised by one interrogation of one artifact is one opinion stated three
times, and it currently fires the signal. Measured on the corpus as it stands:

| category | findings | cycles | fires today |
|---|---|---|---|
| missing-case | 30 | 2 | yes |
| internal-contradiction | 20 | 2 | yes |
| unfounded-claim | 19 | 2 | yes |
| duplicated-truth | 4 | 1 | yes |
| unresolvable-reference | 4 | 1 | yes |
| charter-violation | 3 | 1 | yes |
| untestable | 3 | 2 | yes |
| ambiguity | 2 | 2 | no |

A signal that fires on everything is not a signal. The comment also says *theme* while the code
keys on `category`, which is one of eleven values and therefore close to free to collide.

**2 · The artifact that drew the suggestions does not mention them.**
A suggestion is reported in four places — the findings document, the retro table, the suggestions
file at landing, and the cluster query — and **not one of them is the artifact under review.**
`.sdlc/suggestions/` does not exist in this repository, because it is written at landing and nothing
has landed. So the present state is thirty-two suggestions against `spec.md` with no reader and no
marker.

**3 · `unclassified` is filed as a suggestion about the artifact.**
`workflows/interrogate.js:593` is the only line in the tree that assigns a state:

```js
const state = (c.category === 'unclassified' || !citesOk) ? 'suggested' : 'blocking'
```

Two unrelated conditions share one branch. *Could not be cited* is a real observation that failed to
earn a halt. *Could not be categorised* is not an observation about the artifact at all — it is a
report that the eleven categories did not fit, which is what the `unclassified-rate` health metric
exists to track. Filing it as a suggestion puts a statement about the taxonomy into the evidence
pile about the charter.

## What this intent is not

**It does not promote any of the eighty-five.** Nothing here turns a suggestion into work.

**It does not add a state.** The charter's state table describes three states and the tree writes
two — `open` is accepted by every schema and script and assigned by nothing. That asymmetry is a
charter question, named in the out-of-scope list rather than answered here.

**It does not reduce the pile.** Change 3 removes **zero** findings from today's corpus, because
zero of the 145 are `unclassified`. It is a guard against the pile becoming the default dump, not a
cleanup.

## How we will know it worked

- A corpus of fewer than three cycles reports **no** clusters, and a cluster appears only when the
  same category and stage recur in three or more **distinct** cycles. The current corpus is the
  first test and its expected output is nothing.
- Opening `.sdlc/cycles/<id>/spec.md` shows how many suggestions it drew, and a named check fails if
  that number disagrees with the findings documents. The number is **maintained by the script that
  files the findings**, not by hand — an unbound second copy of a count is the defect INV-03 forbids,
  and is why version 2 deleted the `Applies-to` matrix and version 4 deleted the Coverage column.
- An `unclassified` finding still reaches the corpus, so `unclassified-rate` keeps its input, and
  does not reach the suggestions file.

## What happens when it fails

- **The 3-cycle floor is wrong.** Likely, and unknowable until roughly ten cycles exist. It is one
  integer in one script with a test naming it, so it is cheap to move; the failure mode is a signal
  that stays silent for a year, which is strictly better than one that shouts on day one.
- **`(category, stage)` is still too coarse.** Also likely. Theme-level clustering needs a closed
  vocabulary, and a closed vocabulary is a charter-level list like the taxonomy itself. This change
  makes the key finer without inventing one, and the cluster count is the evidence for whether that
  was enough.
- **The count field drifts.** That is what the check is for, and the check is the reason the field is
  legal under INV-03 at all. If the check cannot be made to pass reliably, the right answer is to
  delete the field rather than weaken the check — the rule this document already records is that
  derived data in a hand-maintained place gets deleted, not promised.
- **Removing `unclassified` from the suggestion report hides a real finding.** Possible. It stays
  filed, stays in the corpus, and stays in the retro table, so it is recoverable from three places.
  Nothing is deleted.
- **It cannot verify.** Certain, today: two mechanical checks report false positives on this
  repository and the verification outcome blocks on both, so no cycle here passes verification until
  `20260926-46a0` lands its scanner fixes. This cycle is **sequenced behind that one** and says so
  rather than discovering it at verify. It is not `blocked-by` — nothing about it is unanswerable,
  and blocking discards the worktree.

## What is out of scope

- **A fourth finding state, and the dead `open` state.** The charter owns the state table. The
  question worth asking there is why it describes three states when two are written, not whether to
  add a fourth.
- **Giving suggestion triage a trigger.** The charter says a suggested finding is dispositioned
  "later, when the suggestions file is triaged" — no cadence, no owner, no trigger. Blocking findings
  are enforced to a person by `tools/Get-SdlcVerifyOutcome.ps1:250`; suggestions are enforced to
  nobody. That is the real gap in reporting, it is a charter amendment, and it is still open from the
  charter's first interrogation.
- **Making a charter cycle land.** A charter cycle has no landing step, so `20260926-bc24`'s
  thirty-eight suggestions will never reach a suggestions file. Real, separate, and not fixable from
  inside the signals script.
- **Feeding the taxonomy rate from a provenance count.** The clean version of change 3 stops filing
  `unclassified` as a finding entirely and counts it instead — which needs the count to survive into
  the corpus, which needs a retro schema field, which is a schema change and a decision. The scoped
  version keeps the finding filed and excludes it from the report.
- **Theme-level clustering**, per above.
- **The two scanner false positives and the charter gate.** `20260926-46a0` owns those.
- **The intent's and the charter's frontmatter.** Both leave their cycle through their own gate — the
  intent merges to master before the cycle branch exists, and the charter's frontmatter is gated by
  INV-08 — so a machine-maintained count on either means rewriting an approved document. Their
  suggestions reach a reader through the cycle's suggestions file. This is an asymmetry, not a
  principle, and it is stated because the spec has to answer it.
