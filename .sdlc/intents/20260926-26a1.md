# The landing script cannot run, because the artifact it requires is the one that disqualifies the cycle

`tools/Complete-SdlcCycle.ps1` is the last step of every cycle and **it has never executed.** Not
once, in any cycle. Three lines in two files make it unreachable:

| Where | What it requires |
|---|---|
| `Complete-SdlcCycle.ps1:89` | the cycle's state is exactly `awaiting-landing`, or it throws |
| `Complete-SdlcCycle.ps1:238` | `retro.md` is on the branch, or it refuses `refused-no-retro` |
| `Get-SdlcCycleState.ps1:238` | a retro exists, so the state is `done` |

Without a retro it fails its own step 4. With a retro it fails its own precondition. There is no
input that satisfies both, so **the tool has no working landing step** and `20260926-46a0` landed by
hand — every one of the script's steps carried out in its order by a person reading the script.

## What is actually wrong

Not the ordering of the `if`. The defect is that **the derivation treats writing the retro as
completing the cycle**, and the retro is written *before* the merge by the script's own design.

`Get-SdlcCycleState.ps1` says so in its own header: *"The retro is the completion certificate: it is
written only at landing."* `Complete-SdlcCycle.ps1` says so too, and more precisely: *"the retro must
be on the branch before anything merges"* — because the retro rides in with the squash so that one
cycle is one commit and `git revert` of a cycle is one operation.

Both are right about the mechanics and the derivation drew the wrong conclusion from them. *Written
for landing* and *landed* are different states, and only the second is done. A retro sitting on an
unmerged branch is a cycle **ready** to land.

## Why this is worth its own cycle rather than a line of repair

**It is the only defect found so far that makes a stage unreachable.** Every other instrument defect
recorded in `20260926-46a0`'s retro degrades a measurement; this one removes a step. And it removes
the step that writes the suggestions intake, merges the target back in, re-verifies and opens the
pull request — so every cycle that lands by hand is a cycle whose landing was not the one the tool
describes.

It also cannot be verified by the cycle that fixes it. This cycle will land by hand too, because the
fix is not on master while it is being reviewed. That is stated here rather than discovered at the
end.

## How we will know it worked

- `Complete-SdlcCycle.ps1` **runs** against a cycle that has a verification and a retro on its
  branch, and reaches its pull-request step. That is the observable test and nothing currently
  produces it.
- A cycle whose retro is on the merge target reads `done`, and a cycle whose retro is only on its
  branch reads `awaiting-landing`. Both directions, because a predicate that answers one correctly
  and the other by accident is the defect being fixed.
- The two headers that describe the retro's timing say what the code does. One of them is the reason
  this took a person reading both files to find.

## What happens when it fails

- **A cycle reads `awaiting-landing` forever after it lands.** The failure mode that matters most: a
  dispatcher reading that queue would offer to land a cycle that is already on master. The header
  already warns about its mirror image — a naive derivation relaunching every completed cycle — so
  the new predicate has to be right in both directions, not merely different.
- **The predicate needs git where the old one needed only the filesystem.** `Test-Path` cannot tell a
  retro on a branch from a retro on master, because both are simply present in the working tree. So
  the answer moves from disk to a ref lookup, and a repository with no `master` has to degrade to
  something honest rather than throw.
- **`Complete-SdlcCycle.ps1` runs for the first time and does something wrong.** Likely, and the
  reason its first execution should be against a throwaway repository rather than this one. It
  merges, commits, pushes and opens a pull request; a defect in any of those is a defect in an
  irreversible-looking step.

## What is out of scope

- **The other six instrument defects** recorded in `20260926-46a0`'s retro, including the one that
  bites soonest: `orphan-annotations` is computed against a single spec's criteria, so it breaks on
  the next cycle that annotates a test. Real, separate, and not a blocker the way this is.
- **`Complete-SdlcCycle.ps1`'s re-verification running `dotnet test` directly** rather than the
  verification outcome script, and hardcoding `dotnet`. A pack concern, and touching it here would
  mean changing what landing *means* in the same change that makes landing *possible*.
- **Whether a plan's `approved:` field should gate landing.** It gates dispatch today and the landing
  script does not read it. A real question about where the human sign-off belongs, and it is a
  charter-level one.
- **The suggestion-reporting changes** in `20260926-c88f`, whose intent is merged and whose spec is
  written. This cycle is sequenced ahead of it only because c88f cannot land until landing works.
